# База данных ST96

> Обновлено 2026-11-05. Одна база Supabase — `st96_platform`, ref `ljatihrxiuouukakbdtb`
> (Postgres 15+, Auth, RLS, pg_cron, pg_net, Storage). Сайт, админка и бот работают
> с одной базой; отдельных баз «для сайта» и «для CRM» нет и не нужно.

## 1. Как устроено сейчас и куда идём

| Состояние | Что это значит |
| --- | --- |
| Было (миграции `0001`–`0014`) | Все 24 таблицы и представление `client_notes` лежали в схеме `public` — схеме Supabase по умолчанию. |
| **Стало (миграция `0015`, применена 2026-11-05)** | Все объекты платформы — в схеме **`crm`**; в `public` таблиц нет, она осталась «входной дверью» PostgREST. Код ходит в `crm` через `SUPABASE_SCHEMA=crm` / `VITE_SUPABASE_SCHEMA=crm`. Exposed schemas: `public, graphql_public, crm`. Проверено на проде: 24 таблицы + представление, 23 политики RLS, 16 внешних ключей, cron-задачи с `crm.*`, данные на месте (69 клиентов, 65 заявок). |

Почему не «схема сайта»: **у сайта своих таблиц нет.** Формы сайта (`/api/lead`),
запись `/book` и всё остальное пишут через серверные функции Vercel с service-ключом,
то есть сайт — клиент API, а не владелец данных. Граница «сайт / CRM» проходит по
`api/*`, а не по схеме Postgres. Разделять нужно не «сайт и CRM», а **внутренние данные
платформы (`crm`) и служебную схему Supabase (`public`)**.

Миграция `0015` проверена дважды: сначала на копии схемы (локальный Postgres 16:
`0001`–`0014` + `0015` проходят чисто), затем применена на проде 2026-11-05 по шагам §6.

## 2. Карта таблиц (все — данные CRM, схема `crm`)

### Клиенты и заявки

| Таблица | Что хранит | Пишет | Читает |
| --- | --- | --- | --- |
| `clients` | карточка клиента: Telegram (`tg_user_id`, `tg_username`), имя, телефон, почта, компания, язык, источник, согласие (`consent_at`), отписка, тема в группе (`admin_topic_id`), `human_until` (бот молчит, пока диалог у человека) | бот, `/api/lead`, `/api/ingest`, админка | все |
| `leads` | заявка: клиент, источник (`site_form`, `booth`, `group`, `manual`), услуга (`service_key`), статус, интересы (`interests text[]`), комментарий | бот, `/api/lead`, `/api/ingest`, админка | все |
| `lead_notes` | заметки сотрудников и комментарии к заявке (полнотекстовый поиск через `text_norm` + `pg_trgm`) | админка, бот, триггер `leads_comment_note` | все |
| `client_notes` (представление) | заметки, привязанные к клиенту напрямую или через заявку; `security_invoker` | — | админка |
| `messages` | переписка с клиентом (входящие/исходящие, тип, медиа, id в Telegram) | бот | админка |
| `tags`, `client_tags` | метки клиентов и связь многие-ко-многим | админка | админка |

### Воронки и очередь

| Таблица | Что хранит |
| --- | --- |

## 3. Правила (не нарушать)

1. **Доступ:** сервер (бот, `api/*`) работает с `service_role` — RLS не ограничивает.
   Браузер (админка) — с publishable-ключом и входом Supabase Auth; данные видит только
   тот, кто есть в `admins` (`crm.is_admin()`).
2. **Новая таблица:** включить RLS, добавить политику «admins full access» (или `admins read`),
   добавлять в существующую миграцию нельзя — только новая миграция с номером.
3. **Медиа** (шаблоны, рассылки) — в Storage, бакет `media` (публичный на чтение по ссылке,
   писать могут только админы); в БД хранится только URL.
4. **Расписание** — `pg_cron`: `st96-run-jobs` (каждую минуту дёргает `/api/jobs`),
   `st96-clean-updates` (чистка `processed_updates` в 03:17). Команды заданы текстом —
   при переезде схемы их надо пересоздать (это делает `0015`).
5. **Функции** `is_admin`, `norm`, `claim_jobs`, `claim_broadcast_recipients`,
   `clients_by_note_words`, `analytics_*` — вызываются из кода через `.rpc()`.
   При смене схемы `search_path` функций должен указывать на `crm, public`.
6. **Секреты** — только в переменных Vercel, не в коде и не в SQL.

## 4. Переменные окружения базы

| Переменная | Где | Значение |
| --- | --- | --- |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Vercel (серверные функции) | проект и сервисный ключ |
| `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` | Vercel (сборка) | публичные значения для админки |
| `SUPABASE_SCHEMA` | Vercel (серверные функции) | `public` до миграции 0015, `crm` после |
| `VITE_SUPABASE_SCHEMA` | Vercel (сборка) | `public` до миграции 0015, `crm` после |

Код читает схему в `crm/server/env.ts` (`dbSchema()`), `crm/server/repo.ts`,
`crm/server/adminAuth.ts`, `crm/admin/supabase.ts`. Если переменная не задана — `public`,
то есть текущее поведение сохраняется.

## 5. Миграции

- Каталог: `crm/supabase/migrations/`, имена `NNNN_тема.sql`, применяются по порядку вручную
  в SQL-редакторе Supabase (владелец) — CLI/`supabase db push` не используем.

## 6. Как применять миграцию схемы (по шагам `0015`, уже выполнено 2026-11-05)

1. Бэкап: Supabase → Database → Backups (или `pg_dump`).
2. SQL-редактор Supabase → выполнить `crm/supabase/planned/0015_crm_schema.sql` целиком.
3. Supabase → Settings → API → **Exposed schemas**: добавить `crm`
   (иначе PostgREST ответит «schema must be one of the following»).
4. Vercel → Environment Variables: `SUPABASE_SCHEMA=crm`, `VITE_SUPABASE_SCHEMA=crm` → redeploy.
5. Проверить: `/admin` открывается, заявка с сайта создаётся, `/book` показывает слоты,
   `/api/jobs` отвечает 200.
6. Откат: восстановить бэкап из шага 1 (или вернуть `set schema public` обратно тем же списком).

Без шага 3 и 4 ничего не заработает — код и PostgREST должны указывать на одну схему.
