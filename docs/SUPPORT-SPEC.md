# Поддержка клиентов (ИИ-агент): ТЗ

Статус: план, согласован по бизнес-логике. Реализация — по фазам (раздел = сессия).
Дата плана: 2026-11-19.

---

## 1. Цель и границы

Автоматизировать поддержку существующих клиентов: клиент пишет в Telegram, ИИ-агент
в рамках оплаченного пакета уточняет детали, вносит правки в его проект (workspace),
деплоит и получает подтверждение. Если запрос выходит за пакет/лимит — агент выставляет
ссылку на оплату (физлицо) или счёт (юрлицо) и ждёт подтверждения оплаты админом.
В любой момент в диалог может подключиться человек: ИИ встаёт на паузу, слушает,
продолжает только по команде /startai.

Вне рамок первой версии: голосовые ответы клиенту, автоматический эквайринг с
колбэком, мультиязычные счета, SLA-эскалации по таймеру.

---

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Боты | Один клиентский бот — @st96_leads_bot (webhook на Vercel). @tolyanagentbot остаётся личным ассистентом владельца; из него переиспользуется только ACP-механика серверного worker-а. |
| «Проект» | Workspace-папка в Harness: /home/dsh/work/<slug> + git-репозиторий + деплой-таргет. Регистрируется в CRM вручную админом. |
| Пакеты | Базовый / Стандартный / Премиум — seed, дальше админ создаёт и редактирует любые пакеты и лимиты в админке. |
| Лимиты | Числовые: корректировки, новые функции, (опц.) обращения. null = без лимита. Базовый: функции = 0 → разовая оплата или апгрейд пакета. |
| Период | Месяц от даты подтверждения оплаты (вариант B). Следующий период — после подтверждения новой оплаты. Лимиты — снимком на период; в конце периода неиспользованные сгорают (без переноса). |
| Единица | Одна правка = 1 корректировка. Обращение может содержать несколько правок; агент их считает до деплоя. |
| Списание | После успешного деплоя (перед деплоем — предупреждение клиенту с остатком). |
| Не хватает правок | Агент публикует часть правок (на остаток), остальные — после оплаты. |
| Смена пакета в середине периода | Пересчёт по остатку дней: стоимость оставшихся дней зачитывается в оплату нового пакета, клиент доплачивает разницу. Активация после подтверждения оплаты. Если лимиты исчерпаны — остаток дней не переносится. |
| Оплата | Физлицо — ссылка на оплату; юрлицо — счёт. Подтверждение — вручную админом. |
| Передача человеку | Сотрудник пишет в теме → ИИ пауза; /startai → продолжает с учётом переписки. |

## 3. Архитектура

Два контура, мост — CRM (Supabase) и HTTP с секретом.

~~~
Клиент ⇄ @st96_leads_bot (Vercel, webhook, grammY)
             │
             ▼
        CRM: clients / support_jobs / package_periods / invoices
             │                              ▲
             │  job (queued)                │  результат (POST /api/support-result, secret)
             ▼                              │
   Worker на сервере (systemd):  dsh --profile acp
             в /home/dsh/work/<проект клиента>
             правки → тесты → git push → deploy
~~~

- Telegram — только Vercel. Worker не делает getUpdates; входящие и исходящие —
  через @st96_leads_bot (одна точка логов, rate-limit, тем группы).
- Агент — только сервер. У Vercel нет файловой системы workspace и долгоживущего
  процесса. Worker — новый сервис (по образцу dsh-tg-bot.service, но без Telegram).
- Асинхронность. Агент работает минуты: бот сразу отвечает «Принял, работаю»,
  результат приходит позже отдельным сообщением.
- Тема группы — существующая (clients.admin_topic_id). Ответы ИИ дублируются
  в тему с пометкой «Ассистент», сообщения клиента — как сейчас.

## 4. Модель данных (миграция 0016, схема crm)

### 4.1 Изменения существующих таблиц

- clients: client_kind (individual|legal), legal_name, unp, legal_address, bank_details.
- leads: client_kind (из поля «Вы обращаетесь как»).

### 4.2 Новые таблицы

packages — настраиваемые админом пакеты
code, title, description, price, currency, period (month),
corrections_limit, features_limit (null=∞), requests_limit (null=∞),
features_allowed (текст: что входит), sla_note, is_active, sort_order.

client_projects — проект клиента
client_id, package_id, workspace_path, repo_url, deploy_target,
default_branch, deploy_cmd, status (active|paused|closed), agent_scenario_id.

agent_scenarios — рамки агента на проект
client_id, project_id, system_prompt, scope_notes, stop_conditions,
allowed_actions, version.

package_periods — периоды с оплатой и снимком лимитов
project_id, period_start, period_end, status (pending_payment|active|expired|blocked),
payment_id, corrections_limit, features_limit, requests_limit (снимок),
corrections_used, features_used, requests_used.

support_jobs — очередь обращений
client_id, project_id, message_id, request_text, status
(queued|running|clarify|ready|deployed|split|out_of_scope|awaiting_payment|failed),
edits_json (список правок), edits_count, result_json, tokens_used,
started_at, finished_at.

invoices — счета и ссылки
client_id, project_id, period_id, kind (period|feature|upgrade),
amount, currency, status (draft|sent|paid_confirmed|cancelled),
link_or_file, confirmed_by, confirmed_at.

agent_audit_log — журнал действий
client_id, project_id, job_id, actor (ai|human|admin),
action, payload (jsonb), created_at.

### 4.3 Нумерация

Миграция 0016_support.sql; RLS: админы — полный доступ, бот — сервисная роль.

## 5. Бизнес-процессы

### 5.1 Подключение проекта

1. Админ создаёт workspace/репо под договор (в Harness, вручную).
2. В админке → «Поддержка → Клиенты/Проекты»: выбрать клиента, вписать
   workspace_path, repo_url, deploy_target, deploy_cmd.
3. Назначить пакет и сценарий агента.
4. Период pending_payment; после первого подтверждения оплаты — active.

### 5.2 Обращение клиента

1. Клиент пишет в @st96_leads_bot. Если у клиента активный client_project —
   сообщение уходит в поддержку (иначе — как сейчас, воронки).
2. Бот: «Принял, уточняю детали» + пересылка в тему.
3. Worker: агент по сценарию разбирает обращение, считает правки (edits_count).
4. До деплоя: проверка остатка и предупреждение клиенту:
   «В обращении N правок, осталось M. Этого достаточно» / «недостаточно».
5. Достаточно → агент уточняет детали → правит → тесты → деплой → клиенту
   «готово, посмотрите» → после подтверждения клиентом списать N.
6. Недостаточно → агент делит на деплоируемые части: публикует на остаток, остальное
   перечисляет и предлагает оплату → invoices → awaiting_payment.
7. Всё — в agent_audit_log и в теме.

### 5.3 Оплата

- Физлицо: ссылка на оплату (настройка в админке; на старте — произвольная ссылка).
- Юрлицо: счёт из шаблона с реквизитами клиента и студии (данные из карточки).
- Подтверждение — админ вручную: paid_confirmed.
- После подтверждения: период активируется / лимит функций увеличивается / смена
  пакета применяется.

### 5.4 Человек в диалоге

- Сотрудник пишет в теме → ИИ пауза (расширение human_until / support_sessions).
- ИИ не отвечает клиенту, но слушает и копит контекст.
- /startai в теме → ИИ продолжает с учётом переписки людей и существующего контекста.
- В момент паузы — резюме контекста в тему (что хотел клиент, что сделано, что осталось).

### 5.5 Смена пакета в середине периода

- **Деньги:** стоимость оставшихся дней текущего пакета зачитывается в оплату нового.
  Клиент доплачивает разницу (апгрейд); при даунгрейде положительная разница
  зачитывается в счёт следующего периода (деньги не возвращаются).
- **Лимиты:** пересчитываются по остатку дней пропорционально, использованное
  сохраняется. Пример: Стандартный (5 правок), осталось 15 из 31 дня, перешли на
  Премиум (10) → новый лимит на остаток ≈ 10×15/31 = 5, потраченное вычитается.
- Активация — после подтверждения доплаты админом; история периодов сохраняется.
- **В конце оплаченного периода все неиспользованные лимиты сгорают** — переноса
  на следующий период нет.
- **Если лимиты исчерпаны** — оставшиеся дни не переносятся и не зачитываются
  в оплату нового пакета: новый пакет оплачивается полностью.

## 6. Админка: раздел «Поддержка»

Новый пункт меню /support, вкладки:

1. Клиенты/Проекты — карточка: project (workspace, репо, деплой), пакет, период,
   остатки, кнопка «сменить пакет», «сценарий».
2. Пакеты — список + редактор всех полей, вкл/выкл, копирование.
3. Обращения — очередь, статусы, правки, ручная корректировка счётчика.
4. Счета — шаблон счёта (физ/юр), выставленные счета, подтверждение оплаты.
5. Настройки — ссылка на оплату физлица, реквизиты студии, разовые цены функций.

## 7. Серверный worker

- Отдельный процесс (systemd), по образцу ST96/bot, без Telegram.
- Читает support_jobs (или получает по HTTP), запускает
  dsh --profile acp с cwd = workspace проекта.
- Промпт job = сценарий + пакет/лимиты + история диалога + текст обращения.
- Результат — POST /api/support-result (секрет в env) → бот отправляет клиенту
  и в тему.
- Изоляция: агент видит только свой workspace; запрет на чтение чужих папок,
  secrets/, .env, ~/.dsh.
- Аудит каждого действия; лимит токенов на клиента; rate-limit.

## 8. Фазы и критерии приёмки

### Фаза 0 — Данные и инфраструктура (core)
- Миграция 0016_support.sql: все таблицы §4, RLS.
- Типы и методы Repo (MemoryRepo для тестов).
- Приёмка: миграция применяется на Supabase; Repo-тесты зелёные; npx tsc -b без ошибок.

### Фаза 1 — Заявка и карточка (leads)
- Поле «Вы обращаетесь как: Частное лицо / Юридическое лицо» в форме сайта и в
  ручной заявке; при «юрлицо» — название, УНП.
- Парсер и LeadInsert; карточка клиента показывает тип и реквизиты.
- Приёмка: leads/*.test.ts зелёные; заявка с сайта сохраняет тип; карточка
  показывает поля.

### Фаза 2 — Админка «Поддержка» (admin)
- Раздел /support с вкладками §6: пакеты (CRUD), проекты, обращения, счета.
- Приёмка: npx tsc -b && npm run build; пакет создаётся/правится/выключается;
  проект привязывается к клиенту; счёт формируется из карточки.

### Фаза 3 — Worker + агент (support, сервер)
- Сервис worker-а; очередь; запуск dsh acp; сценарий; лимиты; аудит.
- Приёмка: тестовый проект: внештатный запрос → clarify; штатная правка →
  deployed; превышение → out_of_scope / awaiting_payment; всё в аудите.

### Фаза 4 — Бот и гейт человека (bot)
- Маршрутизация «есть проект → поддержка»; дублирование ответов ИИ в тему;
  предупреждение об остатке до деплоя; пауза /startai; резюме контекста.
- Приёмка: bot.test.ts зелёные; сценарий «клиент→ИИ→человек→/startai→ИИ»
  проходит в тесте.

### Фаза 5 — Оплата и периоды (support + core)
- Ссылка/счёт, ручное подтверждение, активация периода, счётчики, split-оплата.
- Приёмка: подтверждение оплаты создаёт/активирует период, обнуляет счётчики;
  после split-оплаты агент доделывает оставшиеся правки.

## 9. Открытые уточнения

1. Разбиение правок на деплоируемые части: если правки зависят друг от друга,
   агент определяет группы; спорные случаи — на усмотрение человека в теме.
2. Разовые цены функций и цены апгрейда — где задаются (вынести в «Настройки»).
3. Даунгрейд: подтвердить, что разница зачитывается в следующий период (так
   заложено), а не возвращается деньгами.

---

## 10. Риски

- Промпт-инъекции: текст клиента → агент с правом правок и деплоя. Обязательны:
  жёсткий сценарий, запрет на инструкции из чата вне рамок, аудит, гейт перед деплоем.
- Изоляция workspace: клиент A не должен видеть проект B и секреты сервера.
- Деньги: подтверждение оплаты — только админ; никакого автоподтверждения.
- Токены: лимит на клиента, иначе «дорогой» клиент съедает бюджет.
- Откат деплоя: нужен план отката (Vercel rollback / git revert).
