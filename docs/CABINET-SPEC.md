## 1. Задача

Сделать единое место, где клиент студии видит свою поддержку и покупки: пакет, остаток
кредитов, задачи с расходами, свои проекты, корзину, заявки и все закрывающие документы.
Сейчас это разорвано: пакеты продаются на странице /support, задачи и лимиты живут в
Telegram-боте, проекты — в админке, счета — в переписке и админке. Клиент не видит
целостной картины и не может сам оплатить докупку.

Требования владельца (1–8) закрываются так:

| № | Требование | Решение в кабинете |
| --- | --- | --- |
| 1 | Его пакет; если нет — предложить купить | Карточка пакета на дашборде по каждому проекту; пустое состояние — 4 пакета с кнопкой «Купить» |
| 2 | Остаток кредитов | Крупная цифра «Осталось · N кредитов», прогресс расхода за период, расшифровка «куплено / израсходовано / докуплено» |
| 3 | Задачи с потраченными кредитами | Раздел «Задачи»: дата, задача, проект, статус, кредиты; фильтры, карточка задачи |
| 4 | Проекты, привязанные к клиенту | Раздел «Проекты»: название, домен, платформа, пакет, остаток кредитов, период, статус |
| 5 | Кнопки «купить/докупить кредиты» на странице Поддержки → Корзина; выбор физ/юрлица | Кнопки на /support кладут товар в серверную корзину; в корзине выбор «Частное лицо / Юридическое лицо» и реквизиты |
| 6 | Google-авторизация до корзины; завершение регистрации через Telegram; карточка клиента; все покупки → заявки | Google OAuth (Supabase Auth), обязательная привязка Telegram, создание/слияние карточки клиента, заказ + заявка в CRM |
| 7 | Все функции связаны с кабинетом | Единая навигация кабинета, вход из шапки сайта и с /support, бот и админка работают с теми же данными |
| 8 | Счета, акты (юрлица) и электронные чеки (физлица) в кабинете | Раздел «Документы»: все файлы со статусами и скачиванием; выпуск при оплате заказа |

## 2. Принятые решения

| Вопрос | Решение |
| --- | --- |
| Вход | Supabase Auth, провайдер Google. Отдельный аккаунт клиента, не админский |
| Связь аккаунта и клиента | Таблица `client_accounts`: `auth.users.id → clients.id`, один Google-аккаунт на карточку |
| Завершение регистрации | Обязательная привязка Telegram через deep-link бота (`/start cab_<token>`). Без неё покупка и оплата заблокированы баннером |
| Карточка клиента | Создаётся при первом входе из данных Google; дополняется анкетой (имя, телефон, компания, тип). При совпадении email/Telegram — связывание или слияние с существующей карточкой |
| Корзина | Серверная, у авторизованного клиента. Позиции: пакет или объём кредитов; проект выбирается в корзине |
| Покупка | Оформление создаёт заказ (`orders`) и заявку в CRM (`leads`), уведомление в группу «Лиды ST96» и клиенту в Telegram |
| Плательщик | «Частное лицо» — ссылка на оплату, после подтверждения электронный чек. «Юридическое лицо» — счёт, после оплаты акт об оказании услуг. Платёжный провайдер и фискальные чеки — позже, механика кабинета от него не зависит |
| Подтверждение оплаты | Вручную администратором в `/admin/support` (как сейчас), идемпотентно; после — активация периода, кредиты, документы. При подключении провайдера добавляется вебхук, ручное подтверждение остаётся запасным путём |
| Пакет и кредиты | На уровне проекта (`client_projects + package_periods`). Кабинет показывает пакет по каждому проекту; остаток — кредиты активных периодов + баланс докупленных кредитов |
| Докупка | Отдельный баланс, который не сгорает: тратится после кредитов периода и сохраняется между периодами |
| Маршруты | `/cabinet/*` внутри сайта (React Router); вход из шапки и с /support |
| Документы | `billing_documents` (счёт/акт/чек), файлы в приватном Supabase Storage, скачивание по подписанной ссылке |
| Выпуск PDF | **Автоматически**: счёт — при создании заказа, акт — при подтверждении оплаты, чек — после оплаты (до провайдера — внутренний PDF). Генерация `pdf-lib` + шрифты сайта, постановка в очередь, ретраи |
| Email-уведомления | **Да**, через mail.ru SMTP (логин/пароль позже, ключи в env Vercel). Очередь `email_outbox`, отправка отдельной Node-функцией |
| EN-версия | **Да**: `/en/cabinet/*` по образцу сайта, словари RU/EN; документы и юридические тексты остаются на языке выпуска |
| Автопродление | **Да**: у пакета проекта есть `auto_renew` (по умолчанию включено, клиент может отключить). За 7 дней до конца периода job создаёт заявку `kind='renewal'`, автоматически выставляет счёт и шлёт уведомления. Автосписание картой — только после подключения провайдера |
| Юридические тексты | Дорабатываются существующие на сайте: политика RU/EN (`/privacy`, `/en/privacy`) + новая оферта (`/offer`, `/en/offer`). План — [legal-texts.md](cabinet/legal-texts.md) |
| Границы v1 | Ручное подтверждение оплаты; без эквайринг-колбэка и возвратов. Автоматические PDF, email, EN и автопродление — в объёме v1 |

### Ответы владельца (2026-11-26)

1. Платёжный провайдер и электронный чек — **позже**; кабинет проектируем на ручном
   подтверждении оплаты, провайдер подключается без переделки экранов.
2. Счёт и акт — **автоматически**, PDF генерирует сервер.
3. Юридические тексты — **доработать существующие на сайте** (политика RU/EN), плюс оферта;
   план правок — [legal-texts.md](cabinet/legal-texts.md).
4. EN-версия кабинета — **да**; email-провайдер — **mail.ru**, доступы позже.
5. Автопродление — **да**, с возможностью отключить.

## 3. Роли и сущности

- **Гость** — может смотреть /support и цены, жать «Купить»; получает Google-вход.
- **Клиент (после Google, Telegram не привязан)** — видит онбординг; покупка/оплата заблокированы.
- **Клиент (полный доступ)** — дашборд, задачи, проекты, корзина, заявки, документы, профиль.
- **Администратор** — существующая админка: заказы, подтверждение оплаты, документы, карточка клиента.
- **Бот @st96_leads_bot** — привязка Telegram, задачи поддержки, транзакционные уведомления.

Сущности: клиент → проекты → периоды (пакет + кредиты); клиент → задачи (кредиты);
клиент → корзина → заказ → счёт/акт/чек; клиент → заявки. Все — в CRM, кабинет лишь окно.

## 5. Ключевые сценарии

### 5.1 Первая покупка (гость → клиент)

1. Клиент на `/support` нажимает «Подключить» на пакете или «Докупить» на объёме кредитов.
2. Открывается модалка «Вход в личный кабинет» → «Продолжить с Google».
3. После OAuth — возврат в `/cabinet`; сервер находит/создаёт карточку клиента.
4. Онбординг: «Завершите регистрацию» → «Привязать Telegram» (переход в бота, ожидание) → анкета
   (имя, телефон, компания, тип) → «Завершить».
5. Выбранный товар уже в корзине (намерение сохранено до входа) → корзина.
6. Выбор плательщика, реквизиты при юрлице → «Оформить заявку».
7. Экран заказа: «Ожидает оплаты», инструкция (ссылка для физлица / счёт для юрлица);
   в дашборде — баннер об ожидающей оплате.
8. Админ подтверждает оплату в `/admin/support` → период активен, кредиты начислены,
   в кабинете появились акт/чек, клиенту пришло сообщение в Telegram.

### 5.2 Возврат клиента

Google-вход (сессия Supabase сохраняется) → дашборд: пакет, остаток кредитов, последние задачи,
проекты, документы. Если Telegram не привязан — только онбординг, без покупок.

### 5.3 Докупка кредитов

Дашборд «Докупить кредиты» или `/support` → товар «N кредитов» в корзину → тот же чекаут.
Кредиты ложатся на отдельный баланс и не сгорают: тратятся после кредитов пакета и
сохраняются при смене периода.

### 5.4 Юридическое лицо

Корзина → «Юридическое лицо» → форма: название, УНП (9 цифр), адрес, банковские реквизиты,
чекбокс «сохранить в карточку» → заявка → счёт формируется автоматически (PDF) →
клиент скачивает счёт в кабинете и платит по реквизитам → админ подтверждает →
акт об оказании услуг появляется в «Документах».

### 5.5 Физическое лицо

Корзина → «Частное лицо» → заявка → кнопка «Перейти к оплате» (платёжная ссылка) →
после оплаты админ подтверждает → электронный чек в «Документах».

### 5.6 Задачи из Telegram

Клиент пишет боту → агент выполняет в рамках пакета → `support_jobs` пополняется →
в кабинете «Задачи» появляется запись со списанием кредитов, статусом и деталями.
Кабинет и бот показывают одни и те же цифры (единый источник — `package_periods`).

## 6. Вход, регистрация и карточка клиента

- Google OAuth через Supabase Auth (тот же проект Supabase, отдельные от админов аккаунты).
- Первый вход: `bootstrap` создаёт `clients` (source=`cabinet`) и `client_accounts`,
  если нет совпадения по email. Совпадение по email → привязка к существующей карточке.
- Telegram обязателен: токен `cab_…`, бот сохраняет `tg_user_id`/`tg_username`,
  кабинет опрашивает статус. Telegram уже занят другим кабинетом → отказ и просьба в поддержку.
- При совпадении с существующей карточкой (бот/заявки) — слияние: проекты, задачи, заказы,
  документы и счета переезжают на «главную» карточку, запись в журнал слияний.
- Карточка клиента: имя, email, телефон, компания, тип (частное/юрлицо), реквизиты юрлица,
  Telegram, язык. Правка — в профиле.
- Пока Telegram не привязан: баннер «Завершите регистрацию», кнопки покупки/оплаты недоступны.

Подробные правила привязки, слияния и состояния — [screens-flows.md](cabinet/screens-flows.md) и
[data-api.md §7](cabinet/data-api.md).

## 7. Корзина, заказ, оплата

**Корзина.** Позиции: пакет (по коду из `/api/packages`) и объём кредитов (ползунок 100–10 000
или бандл). Дубли объединяются, счётчик в навигации. Если у клиента несколько проектов —
в корзине выбор проекта для каждой позиции; докупку можно купить без активного периода и без
проекта — кредиты лягут на баланс клиента. Один заказ = один проект = один плательщик;
смешанная корзина (пакет + докупка) допустима — заказ получает `kind='mixed'`.
Если у клиента 0 проектов, пакет оформляется без проекта: админ привязывает или создаёт проект
в заявке до подтверждения оплаты, после этого активируется период.

**Оформление.** Кнопка «Оформить заявку» создаёт:
- `orders` + `order_items` (снимок цен и названий),
- `invoices` (сумма, статус `sent`),
- заявку `leads` (source=`cabinet`) и уведомление в Telegram-группу,
- очищает корзину.
Повторный клик защищён `idempotency_key`.

**Статусы заказа:** `pending_payment` «Ожидает оплаты» → `paid` «Оплачен» →
`fulfilled` «Выполнен»; также `cancelled` «Отменён», `expired` «Просрочен» (5 дней).

**Оплата.** v1 — вручную: физлицо — платёжная ссылка (настройка `support.payment_link`,
в будущем per-order), юрлицо — счёт по реквизитам. Админ подтверждает оплату — идемпотентное действие,
после которого: период активируется или ставится в очередь, кредиты начисляются, документы выпускаются,
клиент получает уведомление.

**Докупка кредитов.** Отдельный баланс (`client_credit_topups`), который не сгорает:
тратится после кредитов периода, сохраняется между периодами и при смене пакета.

## 8. Пакет, кредиты, задачи, проекты

- **Пакет.** Карточка: название, цена периода, срок действия, прогресс кредитов, кнопки
  «Докупить кредиты» и «Сменить пакет» (ведёт на /support). Нет пакета — оффер из 4 пакетов.
  Несколько проектов — карточка на каждый (единый список) и общий остаток.
- **Кредиты.** «Осталось N» = `Σ(credits_limit − credits_used)` по активным периодам +
  баланс докупленных. Рядом — израсходовано и куплено, дата окончания периода, подсказка
  «кредиты пакета не переносятся, докупленные остаются».
- **Задачи.** `support_jobs` клиента: дата, задача (текст запроса, сокращённый), проект,
  статус (человеческие подписи), списано кредитов. Фильтры по проекту/статусу, детальная панель.
- **Проекты.** `client_projects` с новыми публичными полями `title`/`domain`/`platform`/`public_url`;
  внутренние поля (workspace, repo, deploy) не показываются. Статус, пакет, остаток, период,
  кнопка «Написать в поддержку» (открывает бота).

## 9. Документы

Раздел «Документы» — все закрывающие документы клиента:

| Тип | Кому | Когда | В кабинете |
| --- | --- | --- | --- |
| Счёт | юрлицо | автоматически при оформлении заказа | «Готовится» → «Скачать счёт» |
| Акт об оказании услуг | юрлицо | после подтверждения оплаты | постоянно, «Скачать» |
| Электронный чек | физлицо | после оплаты | постоянно, «Скачать» |

Табы «Все / Счета / Акты / Чеки», строки: дата, тип, номер, заказ, сумма, статус, скачать.
Файлы — приватный Storage, ссылки подписываются на 60 секунд. Пока файл не готов — «Готовится».
Существующие счета из админки переносятся в кабинет миграцией (архив, `meta.legacy`).

**Генерация автоматическая.** Счёт рендерится сразу при создании заказа, акт — при подтверждении
оплаты, чек — после оплаты (до провайдера — внутренний PDF с пометкой; после подключения — чек
провайдера). Рендер идёт очередью: `billing_documents.status='draft'` → PDF в Storage →
`issued` + `issued_at`; при сбое — ретрай и статус «Готовится», админ видит ошибку. Шаблоны,
шрифты и нумерация — в [data-api.md §16](cabinet/data-api.md).

## 10. Что меняется на сайте и в админке

**Сайт:**
- Шапка: ссылка «Личный кабинет» / аватар + чип кредитов.
- `/support` (`site/src/components/sections/Pricing.tsx`): кнопки «Подключить», «Докупить»,
  «Купить кредиты» вызывают `addToCart`; гость — Google-вход; после входа товар в корзине.
- Новые маршруты `/cabinet/*` (layout, защита сессией, редирект на онбординг) и
  `/en/cabinet/*` (тот же layout, словари RU/EN; переключатель языка в профиле и шапке).
- `/api/packages` расширяется ценой/названием (уже публично на сайте).
- Футер: ссылки «Политика» и «Оферта» (RU/EN). Политика дорабатывается под кабинет
  ([legal-texts.md](cabinet/legal-texts.md)); оферта публикуется до продаж.
- Cookie-баннер и форма заявки: актуализировать текст под Google-вход, Telegram и покупки.

**Админка `/admin/support`:**
- Вкладка «Заказы»: очередь, фильтры по статусу/плательщику, детали, «Подтвердить оплату»,
  «Отменить», «Перевыпустить счёт» (fallback, если рендер не удался), «Документы»,
  «Привязать проект» (для пакета без проекта).
- Вкладка «Документы»: все счета/акты/чеки, загрузка, выпуск, аннулирование.
- Карточка клиента: блок «Личный кабинет» (Google email, Telegram, дата входа, заказы, документы).
- Проект: поля `title`/`domain`/`platform`/`public_url`.
- Подтверждение оплаты вызывает серверную логику активации периода и начисления кредитов.

**Email:** письма о заявке, оплате, документах и автопродлении через mail.ru SMTP
(очередь `email_outbox`; ключи `MAILRU_SMTP_USER`, `MAILRU_SMTP_PASSWORD`, `MAIL_FROM` — позже).

**Автопродление:** тумблер в карточке пакета и профиле; за 7 дней до конца периода job
создаёт заявку `kind='renewal'`, автоматически выставляет счёт и уведомляет. Отключение —
в один клик до выставления заявки; после — заявку можно отменить.

**Бот:** ветка `cab_<token>` в `/start` (привязка), транзакционные уведомления о заказе,
оплате и документах. Рассылки — по-прежнему только с согласием.

## 11. Данные и API (кратко)

- Миграция `0024_cabinet.sql`: `client_accounts`, `client_link_tokens`, `cart_items`,
  `orders`, `order_items`, `billing_documents`, `client_credit_topups`, `client_merges`;
  у `client_projects` — `title/domain/platform/public_url`.
- API: `crm/api/cabinet.ts` (bootstrap, summary, tasks, projects, orders, documents, cart, checkout,
  profile, telegram_start/status) и `crm/api/cabinet-admin.ts` (заказы, подтверждение оплаты, документы).
- Изменения в существующем коде (period.ts, repo.ts, packages.ts, bot.ts, jobs.ts, админка и сайт)
  перечислены в [data-api.md §20](cabinet/data-api.md).
- Все клиентские записи — только через API с JWT; `client_id` берётся из токена; RLS — защита
  в глубину. Полные DDL, контракты, RLS и тесты — [data-api.md](cabinet/data-api.md).

## 12. Безопасность и приватность

- Клиент видит только свои данные: projects/tasks/periods/orders/documents фильтруются по `client_id`.
- Внутренние поля проектов и чужие данные не отдаются; документы — только по подписанным ссылкам.
- Цены/кредиты пересчитываются на сервере; корзина — снимок, checkout — сверка.
- Идемпотентность платежей и подтверждений; аудит действий админа; лимит запросов.
- Согласие на обработку ПД фиксируется при регистрации (дата + версия политики).
- Политика обработки ПД дорабатывается по [legal-texts.md](cabinet/legal-texts.md) (Google,
  Telegram, покупки, документы); финальные тексты согласует юрист.

## 13. Состояния и ошибки (обязательные)

- Нет пакета → оффер пакетов, кнопки покупки.
- Пакет истёк → баннер «Продлите пакет», задачи read-only, покупка доступна.
- Мало кредитов (< 20 %) → баннер «Докупить кредиты» + сообщение бота 1 раз за период.
- Telegram не привязан → онбординг, покупка/оплата заблокированы.
- Нет проектов → пустое состояние «Подключим проект после оплаты» (пакет купить можно).
- Пустые корзина/задачи/заявки/документы → человеческие пустые состояния с действием.
- Ожидает оплаты → баннер на дашборде, таймтайм заказа, повторная инструкция.
- Оплата просрочена/отменена → «Повторить заказ» (корзина восстанавливается из позиций заказа).
- Ошибка Google/сети → понятное сообщение и повтор; ошибки полей — рядом с полем.
- Telegram занят другим кабинетом → отказ и контакт поддержки (без автослияния аккаунтов).

## 15. Ответы владельца и что осталось уточнить

Получено 2026-11-26: провайдер оплаты — позже; PDF — автоматически; юридические тексты —
доработать существующие на сайте; EN — да; email — mail.ru, доступы позже; автопродление — да.

Осталось получить/согласовать:

2. **Платёжный провайдер:** когда появится — ссылка на оплату, вебхук, фискальный чек; до этого
   ручное подтверждение и внутренний PDF-чек.
3. **Юрист:** финальная редакция политики RU/EN и оферты; срок хранения документов; порядок
   возвратов; формулировки автопродления и автосписания.
4. **Автопродление:** подтвердить, включено ли по умолчанию для новых пакетов (в проекте — да,

5. **EN-документы:** решено — оферта и акт на английском; PDF-шаблоны RU/EN, язык из `clients.language`.
6. **Один счёт на несколько проектов:** сейчас один заказ = один проект; при необходимости
   добавляется отдельной фазой, дизайн не блокирует.
